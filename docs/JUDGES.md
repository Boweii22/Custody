# Run Custody as a judge

Custody has two distinct ways to inspect it: an interactive viewer of actual recorded evidence and an opt-in local sandbox workspace using your own accounts. Neither requires the author's API keys or access to their private merchant account.

## 1. Inspect the actual recorded decisions

From a fresh clone, with Node 22.13+ and npm installed:

```sh
git clone https://github.com/Boweii22/Custody.git
cd Custody
npm run setup
npm run dev -- --hostname 127.0.0.1 --port 4381
```

Open `http://127.0.0.1:4381/judge`.

The viewer uses sanitized actual decision/provider evidence committed under `evidence/`. Inspect the completed USD 1.00 sandbox refund and the subsequent forged-authority over-refund that was held. Replay is labelled as a replay, uses the recorded decision, and performs no payment. Both existing recorded hosted runs predate the later per-task authorization change; current task-binding tests/evaluations are separately labelled.

This path has no credential requirement, no invented business ledger and no model-token cost. It is an evidence viewer, not a claim that a historical transaction has just executed again.

For a standalone static evidence build, run `npm run build:judge`. The output is `dist-judge/`, with no server payment route or runtime keys. The repository includes a GitHub Pages workflow for this artifact. A workflow file or local build does not prove a public deployment: use the verified published link supplied with the final submission. The hosted owner workspace's access policy remains separate.

## 2. Run the actual provider flow with your own accounts

The author-hosted merchant workspace is intentionally owner-private. To exercise real provider calls independently, use the loopback-only local opt-in.

1. Stop the development server and run:

   ```sh
   node scripts/setup-judge.mjs --enable-local-sandbox
   ```

   This creates or updates the ignored `.dev.vars` file with `CUSTODY_LOCAL_SANDBOX=enabled` and a randomly generated `CUSTODY_LOCAL_AUTH_TOKEN`. A fresh file defaults its seller identity to `local-owner`; an existing file keeps its seller/provider settings. It does not print credentials or create a PayPal/OpenAI account. Keep this file local and untracked.

2. Open `.dev.vars` locally and enter your own sandbox/model values:

   ```dotenv
   CUSTODY_RAIL=sandbox
   CUSTODY_SELLER_ID=local-owner
   CUSTODY_LOCAL_SANDBOX=enabled
   CUSTODY_LOCAL_AUTH_TOKEN=<generated by setup-judge.mjs>
   PAYPAL_CLIENT_ID=<your sandbox business REST app client ID>
   PAYPAL_CLIENT_SECRET=<your sandbox app secret>
   EXTRACTOR_URL=https://api.openai.com/v1/chat/completions
   EXTRACTOR_KEY=<your model API key>
   EXTRACTOR_MODEL=<a compatible model>
   ```

   The model must accept OpenAI-compatible Chat Completions with strict JSON schema, `temperature: 0` and `max_tokens`. Model API usage can incur charges on your own account; a ChatGPT subscription is separate. The recorded integration used GPT-4.1 Mini as returned by OpenAI. Do not enter live PayPal credentials: the adapter's origin is fixed to PayPal sandbox.

3. Restart the local development server on loopback:

   ```sh
   npm run dev -- --hostname 127.0.0.1 --port 4381
   ```

4. Open `http://127.0.0.1:4381`, choose the local sandbox unlock control, and enter the generated local token from your ignored env file. The token authenticates this loopback workspace; it is not an OpenAI key. Do not put it in a URL or share it. Hosted deployments ignore this loopback authorization path.

5. In **Connections**, select **Verify PayPal** or **Verify all connections**. An actual constrained model response and PayPal OAuth response must succeed before processing.

6. Create a small USD sandbox checkout. Approve it using a **different sandbox Personal buyer account**, then return and capture the approved order. The merchant Business account cannot be its own buyer. Verify the order/capture IDs and amount.

7. In **Playbooks**, set a conservative refund cap (for example USD 1.00) and return window. Enable **Refund original payments** only. Leave other unverified playbooks paused.

8. Open **New message**. Independently verify your request, select the trusted order and refund action outside the message, choose its maximum amount, and confirm that task authority. Paste a matching request. **Process message may execute a real sandbox refund**, so submit only an action you intend to authorize.

9. Inspect the actual provider status/reference, receipt and animation. A `pending` or `failed` state is not a completed refund. Use authenticated reconciliation for a saved provider reference; it reads current status and does not resubmit the action. An uncertain operation with no reference requires investigation in PayPal.

The local opt-in uses explicit authentication and is restricted to loopback. Do not bind this checkout to `0.0.0.0`, forward its port, deploy it behind caller-controlled identity headers or use it for production funds. Removing the local flag/token restores ordinary inspection-only development behavior.

## 3. Reproduce the real-model authority evaluation without payment writes

See [`evaluation/README.md`](../evaluation/README.md). Supply your own actual captured sandbox orders. It calls the real model, fetches current PayPal records, and imports the application's pure gates. It never calls the payment writer or changes the application ledger. A historical executed refund receipt can be supplied for the duplicate case; absent prerequisites are reported as skipped.

## Verification commands

```sh
npm test
npm run typecheck
node scripts/smoke-api.mjs http://127.0.0.1:4381
```

The smoke test is for the ordinary unconfigured/inspection boundary; run it in a fresh checkout without the local sandbox opt-in. Software fixtures and mocked provider contracts are labelled tests, not operating data or proof of provider settlement.

## What is deliberately outside the demonstrated story

The acceptance evidence demonstrates sandbox checkout/refund, constrained extraction and an exhausted-balance defense. Other adapter code, a public money-moving arena, an ungated baseline, webhook delivery, full document ingestion and production/multi-tenant deployment are not claimed as verified. The model is not a customer-identity verifier: the merchant remains responsible for checking the customer's right to a refund before authorizing a task.
